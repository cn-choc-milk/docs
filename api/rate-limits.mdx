The Synapse API enforces rate limits on a per-account basis to ensure consistent performance for all users. Limits are applied within a rolling one-hour window and vary by your subscription tier. Every API response includes headers that tell you how many requests you have remaining and when your limit resets.

## Rate limit tiers

Your rate limit is determined by your Synapse subscription plan:

| Tier | Request limit |
|---|---|
| Free | 100 requests / hour |
| Professional | 1,000 requests / hour |
| Enterprise | 10,000 requests / hour |

<Note>
  If you consistently reach your rate limit, consider upgrading your plan or contacting [support@synapse-architect.com](mailto:support@synapse-architect.com) to discuss custom limits.
</Note>

## Rate limit response headers

Every API response includes the following headers so you can monitor your usage:

| Header | Description |
|---|---|
| `X-RateLimit-Limit` | Maximum number of requests allowed in the current window. |
| `X-RateLimit-Remaining` | Number of requests remaining before you are throttled. |
| `X-RateLimit-Reset` | Unix timestamp (seconds) when the rate limit window resets. |

### Reading rate limit headers

The example below shows how to extract and log rate limit information from any API response:

<CodeGroup>

```bash curl
# Pass -i to include response headers in the output
curl -i https://api.synapse-architect.com/api/composio/connected-accounts \
  -H "Authorization: Bearer YOUR_API_TOKEN"

# Response headers will include:
# X-RateLimit-Limit: 1000
# X-RateLimit-Remaining: 987
# X-RateLimit-Reset: 1730462400
```

```typescript TypeScript (fetch)
const response = await fetch(
  'https://api.synapse-architect.com/api/composio/connected-accounts',
  {
    headers: {
      'Authorization': `Bearer ${token}`
    }
  }
);

const limit = response.headers.get('X-RateLimit-Limit');
const remaining = response.headers.get('X-RateLimit-Remaining');
const reset = response.headers.get('X-RateLimit-Reset');

console.log(`Rate limit: ${remaining}/${limit} remaining`);
console.log(`Resets at: ${new Date(Number(reset) * 1000).toISOString()}`);
```

</CodeGroup>

## Handling 429 responses

When you exceed your rate limit, the API returns a `429 Too Many Requests` response:

```json
{
  "error": "Too Many Requests",
  "message": "Rate limit exceeded. Please retry after the reset window.",
  "code": "RATE_LIMIT_EXCEEDED",
  "details": {
    "limit": 100,
    "reset": 1730462400
  }
}
```

<Warning>
  Do not retry immediately after a `429`. Repeated rapid retries will not succeed and may result in your account being flagged for abuse.
</Warning>

## Exponential backoff

The recommended approach for handling `429` errors is exponential backoff with jitter — each retry waits longer than the last, with a small random offset to avoid synchronized retries from multiple clients:

```typescript
async function fetchWithRetry(
  url: string,
  options: RequestInit,
  maxRetries = 4
): Promise<Response> {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (response.status !== 429) {
      return response;
    }

    if (attempt === maxRetries) {
      throw new Error(`Rate limit exceeded after ${maxRetries} retries`);
    }

    // Prefer the reset timestamp from the header if available
    const resetHeader = response.headers.get('X-RateLimit-Reset');
    let delayMs: number;

    if (resetHeader) {
      const resetAt = Number(resetHeader) * 1000;
      delayMs = Math.max(resetAt - Date.now(), 0);
    } else {
      // Exponential backoff: 1s, 2s, 4s, 8s, ... with up to 1s of jitter
      delayMs = Math.pow(2, attempt) * 1000 + Math.random() * 1000;
    }

    console.warn(`Rate limited. Retrying in ${Math.round(delayMs / 1000)}s...`);
    await new Promise((resolve) => setTimeout(resolve, delayMs));
  }

  // TypeScript requires an explicit return here; unreachable in practice
  throw new Error('Unexpected exit from retry loop');
}

// Usage
const response = await fetchWithRetry(
  'https://api.synapse-architect.com/api/composio/connected-accounts',
  { headers: { 'Authorization': `Bearer ${token}` } }
);
```

<Note>
  When `X-RateLimit-Reset` is present, waiting until the reset timestamp is more efficient than arbitrary backoff because you know exactly when capacity will be restored.
</Note>
