## What it is

Jira Autopilot is the product surface that reads monitored Jira issues, classifies them by Salesforce delivery type, and creates governed Blueprints ready for human review and approval. Autopilot is the first stage of the [Jira to Run](/getting-started/jira-to-run) path — it converts a Jira issue into a structured Signal, then proposes a Blueprint, but never begins execution without explicit approval.

The name "Jira Autopilot" refers to this specific product surface. It does not mean unattended execution. Every Blueprint generated by Autopilot requires a human to review and approve it before any specialist work begins.

## When to use it

Use Jira Autopilot when:

- Your Salesforce delivery team tracks work in Jira and wants a governed path from issue to sandbox delivery
- You want metadata-aware Blueprint generation without manually decomposing every Salesforce change into tasks
- You want an audit trail that links Jira issues to specific Runs, artifacts, and governance decisions

## Salesforce delivery example

A business analyst creates a Jira story: **"Add Contract renewal date field to Opportunity"**. The issue enters the **In Progress** column. Jira Autopilot reads the issue, classifies it as a metadata change requiring a custom date field plus layout update, and generates a Blueprint with four tasks assigned to AXIOM (architecture analysis), FORGE (field and layout build), and SENTINEL (deployment validation). The architect reviews the Blueprint, approves it, and a Run begins. No code was written and no sandbox was touched until the architect clicked **Approve**.

## Required access

- Synapse workspace with Jira integration connected
- Jira project added to Autopilot's monitored project list
- Blueprint Approver role to approve generated Blueprints

## How Autopilot fits in the delivery lifecycle

Autopilot sits between Signal and Blueprint in the [Synapse delivery lifecycle](/core-concepts/synapse-delivery-lifecycle):

```
Jira issue (Signal) → Autopilot classification → Blueprint → Approval → Run
```

Autopilot is not the only way to create a Blueprint — users can compose Blueprints manually. It is the way to make Jira your governed entry point for Salesforce delivery work at scale.

## What Autopilot classifies

Autopilot reads the issue summary, description, and labels. It identifies patterns that map to Salesforce delivery categories:

| Category | Example trigger phrases | Blueprint type generated |
|----------|------------------------|--------------------------|
| Metadata change | "add field", "update layout", "create custom object" | Component build with analysis, build, validation tasks |
| Apex development | "apex trigger", "batch job", "invocable method" | Code build with syntax check, PMD scan, test run |
| LWC / Aura | "lightning component", "LWC", "UI change" | Frontend build with ESLint, test, deployment |
| Deployment / release | "deploy to UAT", "promote to staging" | Deployment governance Blueprint |
| Governance / compliance | "governor limits", "code review", "PMD", "security review" | Sentinel-led validation Blueprint |

Issues that do not match any classification category are logged and surface in Autopilot as **Unclassified** for manual review. They are never silently dropped.

For the full classification model and how to tune routing, see [Jira Autopilot — How it works](/autopilot/jira) and [Routing Rules](/autopilot/routing-rules).

## Governance notes

Autopilot classification is a proposal, not a commitment. Every Blueprint generated by Autopilot:

- Is presented for human review before any task is dispatched
- Includes preflight SENTINEL validation results surfaced in the approval panel
- Records the originating Jira issue ID, classification timestamp, and the component types detected

Autopilot never writes to your Salesforce org. It never creates scratch orgs, deploys metadata, or executes specialist tools without an approved Blueprint. The audit trail includes every classification event, every Blueprint generated, and whether the resulting Blueprint was approved, modified before approval, or rejected.

If a Blueprint is rejected, the rejection and rejector identity are logged. The originating Jira issue receives a comment noting that no delivery work was started.
