## What it is

Secrets is the credential store that keeps sensitive values — Salesforce auth tokens, GitHub deploy keys, E2B sandbox keys — outside of prompts and outside of logs. Every credential is encrypted at rest and scoped to the tenant, project, or integration it belongs to. Specialists retrieve credentials by scope at Run time; the plaintext value is never passed through agent prompts or written to audit records.

## When to use it

Store a credential before you connect a Salesforce org, configure a GitHub integration, or launch any Run that needs authenticated access to an external system. If a credential already exists in the vault for the required scope, Runs use it automatically. You rotate credentials here when tokens expire, not by re-entering them in configuration forms or prompts.

## Salesforce delivery example

A Blueprint includes a task that deploys approved metadata to a connected Salesforce sandbox. The specialist assigned to that task needs a valid Salesforce OAuth access token. Rather than passing the token in the Blueprint definition — where it would appear in audit logs and in agent context windows — the deployment task references the `salesforce/default` credential scope. At Run time, the credential vault decrypts and injects the token for that task only. The token is never visible in the Run's activity log or in any specialist prompt.

## Required access

- **Admin or Owner role** — required to add, rotate, or delete credentials
- **Member role** — can view credential metadata (label, service, expiration status) but cannot read or export credential values
- **Service principals** — `service_mastra` can retrieve credentials by scope during Run execution; it cannot list or modify credentials

See `docs/modules/auth/MODULE.md` for the full RBAC matrix.

## Governance notes

- Credentials are never stored in plaintext. See [Encryption](#encryption) below.
- Credential reads are recorded in the application log with the credential label and Run ID. Durable audit-trail capture for credential reads is on the post-launch roadmap.
- Tenant isolation is enforced at the database layer: Row Level Security (RLS) policies prevent any query from returning credentials that belong to a different `tenant_id`.
- Deletion is permanent. Deleting a credential while a Run is in progress will cause any subsequent task in that Run that depends on the credential to fail with a `CREDENTIAL_NOT_FOUND` error.

## Encryption

Every credential value is encrypted using **AES-256-GCM** with a per-write 32-byte random salt and 16-byte IV. The encryption key is derived from a master secret (`CREDENTIALS_VAULT_MASTER_KEY`) via PBKDF2 (SHA-256, 100,000 iterations). The stored record contains the ciphertext, salt, IV, GCM authentication tag, and algorithm identifier — never the plaintext or the master secret. The encrypted record is held in the `credentials_vault.encrypted_value` JSONB column.

Because each encryption call generates a fresh salt and IV, two encryptions of the same credential value produce different stored output.

GCM mode provides both confidentiality (the value is encrypted) and integrity (the authentication tag detects any modification to the stored ciphertext). If the stored data is altered, decryption fails and the Run task receives an error rather than a corrupted or attacker-controlled value.

**Key rotation** is supported without downtime. The `reEncrypt` utility decrypts credentials with the old key and re-encrypts them with the new key before the old key is removed from the environment.

### Where credentials are stored

- **Table:** `credentials_vault`
- **Column:** `encrypted_value` — JSONB object containing `encrypted`, `salt`, `iv`, `tag`, and `algorithm` fields
- **Plaintext is never stored** anywhere in the database

## Credential scopes

Synapse supports two credential scopes, which control where a credential is available during Run execution:

| Scope | Meaning |
|---|---|
| **Tenant-level** | Available to all Runs across all projects in the tenant; one credential per service per tenant |
| **Integration-level** | Available to the integration connection (Jira, Salesforce) it was created for; managed by the connection record |

See [Credential Scopes](./scopes) for worked examples and scope resolution order.

## Rotation

Credentials should be rotated before their `expires_at` date. The vault tracks `last_used_at` and `use_count` on every credential, which helps identify stale credentials that may no longer be needed.

To rotate a credential:

1. Navigate to **Settings → Credentials** in Synapse.
2. Select the service (Salesforce, GitHub, E2B).
3. Click **Rotate** on the credential you want to update.
4. Paste the new credential value and confirm.

The vault overwrites the encrypted value in place. The credential ID, scope, and label do not change, so existing Runs that reference the credential continue to work without reconfiguration.

See [Managing Credentials](./manage) for the full UI walkthrough.
