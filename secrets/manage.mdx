## What it is

Managing Credentials is the administrative workflow for adding new secrets to the vault, keeping them current through rotation, and removing credentials that are no longer needed. All credential management operations require Admin or Owner role and are logged in the audit trail.

## When to use it

Perform credential management when:

- You are connecting a new Salesforce org, GitHub repo, or E2B execution environment and need to store an auth token before the first Run can use it.
- A credential has expired or is approaching its `expires_at` date.
- A team member with access to a credential has left and the token must be rotated as a security practice.
- You need to remove a credential that belongs to a decommissioned project.

## Salesforce delivery example

Your team is connecting a new Salesforce sandbox for a major release. The org administrator generates a Connected App client secret and a CLI auth URL. Rather than sharing the secret in a chat channel or a Blueprint comment, the admin navigates to Settings → Credentials, selects **Salesforce**, and stores the credential. The vault holds one credential per service per tenant; the stored credential is then available to all Runs within the workspace.

## Required access

| Role | Can add | Can rotate | Can view metadata | Can delete |
|---|---|---|---|---|
| **Owner** | Yes | Yes | Yes | Yes |
| **Admin** | Yes | Yes | Yes | Yes |
| **Member** | No | No | Yes | No |
| **Viewer** | No | No | Yes | No |

Credential values (the plaintext secret) are never displayed in the UI to any role. After a credential is stored, the only way to retrieve the value is to rotate it with a new value.

## Governance notes

Every add, rotate, and delete operation is written to the audit log with the performing user's ID, the tenant ID, the service type, the credential label, and the UTC timestamp. The credential value itself is never written to audit records.

## Adding a credential

1. Open **Settings** from the left navigation.
2. Select the **Credentials** tab.
3. Click **Add credential**.
4. Choose the **Service**: Salesforce, GitHub, or E2B.
5. Optionally, set an **Expiration date**. The vault will flag the credential as expired after this date; Runs that depend on it will fail until the credential is rotated.
6. Paste the **Credential value** in the secure input field.
7. Click **Save**.

The system performs a format sanity-check before storing the credential: Salesforce credentials must start with `force://` or `https://`; GitHub credentials must meet the minimum token length. If the check fails, the form displays the error and the credential is not stored. Full validation occurs at first use.

After saving, the credential value is immediately encrypted using AES-256-GCM and the plaintext is not retained anywhere. The form clears the input field.

## Rotating a credential

Rotation replaces the encrypted value in place. The credential ID, service, and tenant scope remain unchanged. Any Blueprint task that references this credential automatically uses the new value on the next Run without reconfiguration.

1. Navigate to **Settings → Credentials**.
2. Find the credential you want to rotate. Use the service filter or search by label.
3. Click **Rotate** (the key icon on the credential row).
4. Paste the new credential value.
5. Click **Confirm rotation**.

The old encrypted value is overwritten. There is no recovery path for the previous value.

**Rotation during an active Run:** If a Run is in progress when you rotate a credential, tasks that have already retrieved the credential use the old value for the duration of that task. Tasks that request the credential after the rotation use the new value. There is no locking mechanism — if you need to ensure no Run uses the old credential, pause or cancel active Runs before rotating.

## Validating a credential

The credential list shows the last-used timestamp and a status badge:

| Badge | Meaning |
|---|---|
| **Active** | Credential exists, has not expired, was used recently |
| **Expired** | `expires_at` date has passed |
| **Never used** | Credential exists but no Run has requested it yet |

Runs that attempt to retrieve an expired credential receive a `CREDENTIAL_EXPIRED` error. The Run task fails and the failure is logged with the credential label and the Run ID. The Run does not fall back to another credential silently.

## Deleting a credential

1. Navigate to **Settings → Credentials**.
2. Click the **Delete** (trash) icon on the credential row.
3. Confirm the deletion in the dialog.

Deletion is permanent and immediate. The encrypted value is removed from the vault. Any Blueprint task or integration configuration that referenced this service credential will fail on the next Run with a `CREDENTIAL_NOT_FOUND` error.

Before deleting, search for usages:

- In **Blueprints**: review task definitions that reference the service type and label.
- In **Integrations**: check connected Salesforce orgs and GitHub configurations under Settings → Integrations.

There is no soft-delete or recycle bin for credentials.
