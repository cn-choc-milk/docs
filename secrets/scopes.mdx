## What it is

Credential scopes define which Runs and specialists can access a stored credential during execution. Synapse supports two levels: tenant-wide and integration-specific. Scoping follows the principle of least privilege: a credential is available only as broadly as the work that needs it.

<Note>
  Per-project credential scoping (restricting a credential to a single project) is on the post-launch roadmap. Until then, tenant-level credentials are accessible to all Runs within the workspace.
</Note>

## When to use it

Choose a scope when adding a credential based on how broadly you want it available:

- Use **tenant-level** for shared service accounts that every project in the workspace uses, including Salesforce org credentials and GitHub deploy keys.
- Use **integration-level** when the credential was created during a Jira or Salesforce connection setup and belongs to that connection's auth lifecycle.

## Salesforce delivery example

A team manages delivery work across multiple projects in one Synapse tenant. All projects use the same Salesforce staging sandbox and the same GitHub service account:

| Service | Scope | Accessible by |
|---|---|---|
| `salesforce` | Tenant | Any Run in the tenant |
| `github` | Tenant | Any Run in the tenant |

Integration-level credentials (OAuth tokens for connected Salesforce orgs and Jira connections) are managed separately through the Integrations page and follow the lifecycle of those connections.

## Required access

- **Admin or Owner** — can add, rotate, and delete credentials; controls which credential is stored per service
- **Member or Viewer** — can see credential metadata (service, expiration status) in the UI, cannot change or read values

## Governance notes

Tenant-level credential access is controlled by service-role enforcement in the API layer. A Run task may only retrieve a credential for the service types it has been granted by the Blueprint's execution context. If the requested service credential is not in scope, the task fails with `CREDENTIAL_NOT_FOUND` — this prevents silent fallback to an unintended credential.

## Tenant-level credentials

A tenant-level credential is stored at the tenant scope. It is accessible to any Run within the tenant. The vault holds **one credential per service per tenant** — storing a new Salesforce credential replaces the existing one.

Use tenant-level credentials for:

- The Salesforce org used for delivery Runs
- A GitHub service account used across all projects
- E2B sandbox API keys used by the execution layer for all Runs

---

## Integration-level credentials

Integration-level credentials are created and managed through the Integrations settings surface (Settings → Integrations) rather than the Credentials tab directly. They are owned by the connection record for a Jira or Salesforce integration.

- **Jira connections**: OAuth tokens are stored as integration-level credentials scoped to the `composio_auth_configs` record. The credential follows the integration lifecycle: when the integration is disconnected, the credential is removed.
- **Salesforce connections**: access tokens and refresh tokens are stored in `salesforce_connections.access_token` and `salesforce_connections.refresh_token` (both encrypted). The `TokenSyncService` manages refresh automatically.

Integration-level credentials are not visible in the Credentials tab. They are managed through the Integrations page. See [Salesforce](../integrations/salesforce) and [Jira](../integrations/jira) for connection setup.

---

## Scope resolution at Run time

When a specialist task requests a credential at Run time, the vault resolves it in this order:

1. **Tenant-level match** — look for a tenant-level credential with the requested service type.
2. **Error** — if no credential is found, the task fails with `CREDENTIAL_NOT_FOUND`.

## Worked example: credentials in one Run

A Run for a Flow migration includes three tasks:

| Task | Credential needed | Scope |
|---|---|---|
| Retrieve Flow metadata from Salesforce | `salesforce` | Tenant-level |
| Push approved changes to GitHub | `github` | Tenant-level |
| Provision execution environment | `e2b` | Tenant-level |

At task execution, the vault looks up each credential by service type for the tenant. All three credentials are delivered to the specialists without the plaintext value appearing in any Run log or specialist prompt.
